## What + why
The patched clangd answers the first `M-.` after a restart from the stored index, but
only from a shard that was indexed without errors; a flagged shard may miss symbols
and references. On RMO five sources carried that flag although they compile: they were
indexed while headers were being edited or did not exist yet, and clangd never
re-indexed them, because at startup it re-indexes only shards whose files changed on
disk (`RESEARCH_navigation_delays.md`). Their first `M-.` waited 7 - 13 s for the
parse, after every restart.

Patch 0009 adds one condition to `BackgroundIndex::loadProject`: a loaded shard with
`HadErrors` schedules its source for re-indexing, like a stale shard does. A source
that compiles now gets a clean shard; one that still has errors gets re-indexed and
stays flagged, so its answers keep coming from the parse, never from a flagged shard.

On RMO (Mac): the first session with the new clangd re-indexed seven sources (log
lines "Reindexing ...: the shard of ... was indexed with errors"), rewrote the five
that compile now and left the two that do not (`main_sparsity.cc`, `m_matrix.cc`, in
the middle of the owner's edits). After a restart:

|---|---|---|
| `src/main_bench.cc` | 12.6 s | 19 ms |
| `src/main_coarse.cc` | 12.0 s | 5 ms |

| `staging/test/gradient.cc` | 8.5 s | 2.7 s |
| `staging/test/lumping.cc` | 8.9 s | 17 ms |

## Concepts explained
- **Stale versus flagged.** A shard is stale when a file it covers has different
  content on disk now; clangd always re-indexes those. A shard is flagged when its
  indexing saw a compile error; until now that alone triggered nothing.
- **Why the missing header matters.** The include graph lists the files a source
  actually included. A header that was "not found" is not in it, so creating the
  header later changes nothing clangd watches. The unit test reproduces exactly that.

## Assumptions + risks  (the postmortem ledger)
- **Assumed:** re-indexing still-broken sources at every start is cheap enough.
  **Would break if:** a large project carries many broken sources; each costs a full
  index run per start (low priority, in the background). **DESIGN bet:** D-060.
- **Assumed:** clangd keeps a flagged shard when the new run also has errors
  (`update()` writes only if the content changed or the errors are gone); seen here
  for the two broken sources.
- **Risk:** the flag is shared by every file of a source's include graph, so a broken
  header schedules its owning source each start until fixed; same cost as above.
