## What + why
S9 showed that a header opened as the first file after a restart always got the
guessed flags on RMO (0027): it asks the index for an includer a moment before clangd
has handed the project to the index, and patch 0005 took "not loading yet" for
"nothing to load". Patch 0006 makes the question wait for that handover first, then
for the stored index to load, within the same 5 s limit.

## Concepts explained
- **`blockUntilIdle`:** every clangd compile database can be asked to finish its
  pending work; for the directory-based one that is the queue of its broadcast
  thread, which announces newly found projects. After it returns, the index has
  received the project and counts its load, so the existing wait applies.
- **Why inside the index:** `includerOf` already holds the compile database it was
  built with, so the fix is in one function, and a unit test can drive it with a
  database that announces its project only when asked to become idle, which forces
  the S9 order every time.

## Key files walked
- clangd `index/Background.cpp` - `BackgroundIndex::includerOf`: deadline, then
  `CDB.blockUntilIdle`, then the wait for the load (outside the index's lock, since

- clangd `unittests/BackgroundIndexTests.cpp` - `AnnounceOnIdleCDB` and

## Assumptions + risks  (the postmortem ledger)
- **Assumed:** waiting for the database's broadcast queue cannot block on the
  header's own worker (the broadcast calls the index's `enqueue` and the language
  server's change listeners, which only queue work). **Would break if:** a header
  open hangs for 5 s; the log then shows the decision 5 s after opening.
  **DESIGN bet:** D-046.
- **Risk:** every file without a reliable command (headers) waits for the database
  once per lookup; after the first handover the queue is empty and the call returns
  at once.
