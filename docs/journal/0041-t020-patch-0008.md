## What + why
When a header has no compile command of its own, the patched clangd borrows one from
a source file that includes it, found through the index (D-028). Before answering,
`includerOf` waited for the compile database to finish announcing projects (patch
0006) and for stored shards to load (0007). The code review (0031) noticed that it
waited even when the answer was already known: harmless most of the time, but up to
5 s whenever the database's announcement thread was busy with another project.

Patch 0008 looks the header up first. A known includer is returned at once; only an
unknown header waits, because that is exactly the case 0006 fixed (a header opened
first, before its project was handed to the index). The counter of loads in progress
was raised in one function and lowered in another; the two are now a named pair,
`projectLoadStarted` and `projectLoadFinished`, defined next to each other. 0007's
long doc comment is wrapped again.

## Concepts explained
- **The new test's trick.** `BusyCDB` is a test compile database whose
  `blockUntilIdle` waits until its deadline while `Busy` is set, as a busy announcement
  thread would. The test indexes a source file, sets `Busy`, and asks for the
  includer of a header the source includes: it must come back within 1 s. Without
  the patch it came back after the full 5 s, and the test failed; with it, it passes.
  The same test checks that an unknown header still waits.
- **Where it was built.** The local clangd tree (`~/source/repos/llvm-clangd`) is on
  the Arch machine. On the Mac the 23.1.1 tarball was turned into a scratch git tree
  with patches 0001 - 0007 applied (`git am`), 0008 written on top, and
  `git format-patch` wrote `packaging/clangd-index-nav/0008-...patch`. The PKGBUILD
  lists it with its checksum (pkgrel 6); `build-macos.sh` reads that list.

## Assumptions + risks  (the postmortem ledger)
- **Assumed:** any recorded includer gives a usable compile command; an includer found
  later during a load would not be better. **Would break if:** two includers need
  different flags for the header; clangd's own includer cache keeps precedence as
  before (D-028).
- **Not taken:** "no stall for headers that have no includer" from the task text;
  that wait is what keeps a header opened first from getting guessed flags (O-21).
- **Risk:** ClangdTests count 1413 on macOS against 1414 on Arch before; some tests
  differ by platform. The Arch run with pkgrel 6 gives the comparable number.
